# Descripción de Pull Request (GitHub)

Generás una descripción de PR **en español**, lista para pegar en GitHub. El objetivo NO es revisar
el código, sino **contar qué se hizo** para tres lectores a la vez:

1. **Otro programador** → qué se cambió y **dónde** (archivos/módulos), para revisar y mantener.
2. **El histórico del proyecto** → registro legible meses después.
3. **Alguien no técnico** → resumen en términos de funcionalidad y valor.

## Paso 1: Detectar contexto de la rama

```bash
git branch --show-current
git remote show origin 2>/dev/null | grep "HEAD branch"

# Rama base: en gymapp los PR van a `main`. `develop` quedó abandonada en abril 2026.
git log --oneline --no-merges origin/main...HEAD
git diff --name-status origin/main...HEAD
git diff --stat origin/main...HEAD
```

Si el usuario te dice que el PR va a otra rama, usá esa. Si no podés determinarla, preguntá.
Si hay trabajo **sin commitear**, avisalo: no entra al PR hasta que se commitee.

## Paso 2: Entender QUÉ se hizo

- Agrupá los commits por tema (no listes commit por commit).
- Identificá el tipo: feature, fix, refactor, performance, infra/config, datos/migración.
- Capturá issues referenciados (ej. `#123`).
- Mirá el diff de los archivos clave para describir con precisión, no en abstracto.
- Si el diff es muy grande (+2000 líneas), procesalo por carpeta y resumí por módulo.

## Paso 3: Mapear DÓNDE se cambió

Agrupá por módulo/responsabilidad, no como lista plana, y con rutas concretas para que sean
clicleables:

- **Backend** — por módulo: `gymapp-back/.../modules/clients/`, `.../payments/`, etc.
- **Migraciones** — `gymapp-back/src/main/resources/db/migration/V<n>__*.sql`.
- **Frontend** — por feature: `gym-frontend/src/features/routines/`, `components/ui/`, etc.
- **Infra/config** — `docker-compose.yml`, `application.properties`, variables de entorno, Dockerfile.

## Paso 4: Generar la descripción

Producí el texto en **español**, con esta estructura, dentro de un bloque de código para copiar. Si
el usuario pide `--file`, guardalo también en `docs/pr/YYYY-MM-DD-<rama>.md` (los `.md` van dentro
de `docs/`, nunca en la raíz — `CLAUDE.md` §6).

```markdown
## Resumen

[2-4 oraciones en lenguaje claro. Qué resuelve este PR y para qué sirve, en términos de
funcionalidad — sin jerga técnica.]

## Cambios principales

- **[Tema 1]** — qué se hizo y por qué (1-2 líneas).
- **[Tema 2]** — ...

## Detalle técnico (dónde)

> Para quien revise o mantenga el código.

- **`gymapp-back/.../modules/<modulo>/`** — [qué se cambió].
- **`gym-frontend/src/features/<feature>/`** — [qué se cambió].
- **Migraciones** — [qué hace la migración nueva, si la hay].
- **Infra/config** — [docker-compose, variables de entorno, si aplica].

## Cómo probarlo

[Pasos concretos: comandos, endpoint, pantalla. Si hay migración nueva, el comando para aplicarla
y qué debería verse. Omitir si no aplica.]

## Notas / pendientes

- [Decisiones de diseño, deuda, breaking changes, variables de entorno nuevas.
  Omitir la sección si no hay nada.]

## Referencias

- [Issues, ej. Closes #123. Omitir si no hay.]
```

## Reglas de redacción

- **Siempre en español.** Tono profesional y directo.
- **El resumen es para cualquiera**: sin nombres de clases ni rutas; hablá de funcionalidad.
- **El detalle técnico es para programadores**: ahí sí van rutas, módulos y términos técnicos.
- **No inventes.** Si algo no surge del diff ni de los commits, no lo afirmes. No agregues secciones
  vacías — omitilas.
- **Agrupá, no transcribas.** No copies el `git log` tal cual; sintetizá por tema.
- **Destacá siempre**: migraciones nuevas (hay que aplicarlas), cambios en el contrato de la API,
  variables de entorno nuevas y breaking changes. Es lo que más rompe a quien traiga la rama.
- **No incluyas líneas de autoría de IA** ni firmas tipo "Generated by".
- Largo proporcional al PR: un PR chico = descripción corta.
